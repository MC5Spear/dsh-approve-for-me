# 需求（dsh-approve-for-me）

> 本文自包含：所依赖的宿主与 codex 事实直接写在正文里，并附公开可查的上游出处（公开 npm 包的 `文件:行号` 或公开 URL）。本文只写「现在要做什么」，不写历史与设计推导。

## 1. 目标

给 DeepSeek Harness（dsh）做一个插件，实现 codex `--approve-for-me` 的等效功能：**沙箱升权等需要审批的操作，先由一个 LLM 审查器逐次判断；判定安全就自动放行，判定危险才交给人工；人工在时限内不响应则自动拒绝，避免任务被无限期阻塞。**

**codex 是行为蓝本**（openai/codex 的 `ApprovalsReviewer::AutoReview` + Guardian 审查会话）。dsh 只是宿主：本插件的审查提示词、结构化输出、决策语义、超时与失败姿态都对齐 codex，再按 dsh 的审批接缝实现：应答者是 `approval/request` waterfall 监听器，签名 `(req, next) => Promise<outcome>`；`req = { agent, toolName, callId?, reason?, signal? }`，不含工具参数；outcome 闭集 `allowed-once | rejected | cancelled | unavailable`；返回 `next()` 委托下一个应答者（`@deepseek-ai/dsh-user-approval@0.1.7-rc.1` lib/index.js 的 `request()` 与 `decide()`）。

**形态固定为「审批应答者」**：保留沙箱，工具撞墙后带 `sandbox_permissions` 请求升权，由审查器逐次判定是否批准这一次升权。宿主 dsh 0.1.7 自带的实验性 `auto` 预设是**另一种形态**（无沙箱 + 逐调用准入），本插件**不采用**——它的执行组合固定为 `danger-full-access` 且审批策略为 `never`（`@deepseek-ai/dsh-permission-presets@0.1.7-rc.1` lib/index.js 的 `AUTO_PRESET_SPEC`），而审批服务对 `never` 会话在 waterfall 分发之前直接返回 `rejected`、不调用任何应答者（`@deepseek-ai/dsh-user-approval@0.1.7-rc.1` lib/index.js 的 `decide()` 短路分支），应答者根本收不到请求。

## 1b. 非目标（本次不做）

- **不采用官方 `auto` 预设的语义**，不调用 `permissionPresets.registerAuto`，不做逐调用准入检查（依据同 §1：`auto` 固定无沙箱＋`never`，`never` 在 waterfall 之前短路；用户已裁定不采用）。
- **不修改宿主任何文件**：不生成也不应用源码补丁，不提供"打补丁档 / 不打补丁档"的切换（R20）。
- **不提供"兼容 0.1.5"的分支或双份实现**：本插件只服务 0.1.7 及以后（R25）。
- **不为记录表缺口造插件侧替代品**：不往会话日志写插件自定义事件类型——持久化读路径对不在已知事件类型清单里的类型一律拒绝，而 `Session.append()` 不提供 `ignorable` 标记（`@deepseek-ai/dsh-session@0.1.7-rc.1` 的 `append` 封装与 `@deepseek-ai/dsh-session-persistence@0.1.7-rc.1` 的校验）；也不覆盖宿主的记录表视图（宿主记录表只渲染 user／steering／assistant／context／compaction／tool-result 六种节点，其它种类被静默跳过）。
- **不把 `permission` 行写进插件自带的 bundle patch**：补丁对目标行是逐键赋值、`config` 键被整段替换，会连带清掉部署方自己的预设表；且 bundle 层序上 `@deepseek-ai/dsh-base@0.1.7-rc.1` 排在第三方包之前，本插件的 patch 压根命中不到该行（`@deepseek-ai/dsh-app-boot@0.1.7-rc.1` 的 `applyEntryPatches` 覆盖语义与层序注释）。
- **0.1.7 线不做 0.2.0 适配与版本区分**：实现与验收都在 0.2.0 线，§2 中 R49/R50 两节全文即该线的现行需求。

## 2. 强制需求

### R1 LLM 审查（不可裁剪）
- 通过规则预筛的审批请求，必须交给 LLM 审查器给出允许/拒绝判断，不得退化为纯静态规则。
- 审查输入至少包含：工具名、真实命令/参数（经 `callId` 回查 PTC 派发事件 `tool/ptc-dispatch-start` 的 `data.arguments` 对象，兼容旧名 `tool/code-dispatch-start`；见 `@deepseek-ai/dsh-tools@0.1.7-rc.1` lib/index.js 的派发处）、工作目录、请求的升权目标模式、发起理由，以及**会话最近上下文**（用户最近请求与助手最近动作，用于判断「用户是否已授权该操作」）。上下文取材方式对齐 codex Guardian 的 transcript 机制。
- 审查输出必须是结构化结果，至少含 `decision: allow|deny`、`risk: low|medium|high`、`reason: string`。
- **决策映射（对齐 codex）**：`allow` → 自动放行（`allowed-once`）；`deny` → **直接拒绝**（返回 `rejected`），并通过 `agent.inject()` 把拒绝原因明确告知主模型；审查超时 / 失败 / 输出不可解析 / 模型不可用 → **直接拒绝**（fail-closed，对齐 codex），同样注入原因；`req.signal` abort → `cancelled`。
- 审查调用自身不得触发新的审批（不得递归）。
- 不得让被审查的 agent 用同一会话自审自批。

### R1b 审查器可自主调用只读工具（重要）
- 审查器在给出判断前，可以自主调用**只读工具**（读文件、搜索、列目录等）收集证据。
- 工具集必须限定为只读；工具调用不得触发新的审批；不得修改工作区。
- 目的：审查没有人工通道托底，若审查器无工具又保守判断，会导致大量命令被误拒。
- 工具调用失败时审查继续（视为无证据），不得因此自动放行或自动拒绝。

### R2 审查器模型：可配置 + 明确的覆盖顺序
用户要求能回答"在哪里设置审查模型、是否按模型/项目/全局设置、按什么顺序覆盖"。必须实现并写入文档：

- 支持的维度：会话级覆盖、全局默认、按父 agent 模型映射。
- 覆盖顺序（先命中先用）：会话级选择 → 按父模型映射 → 全局默认 → 跟随父 agent 当前模型（最后回退）。
- 任一层给出不可用的 provider/model 时降级到下一层，并在审计里记录实际使用的层与路由，不得静默失败。
- 模型解析结果需要缓存与失效策略（父模型切换、设置变更时重解析）。

### R3 超时
- `reviewer.timeoutMs`：LLM 审查超时 → **直接拒绝**（对齐 codex fail-closed），并注入原因。
- `human.timeoutMs`：仅在 `fallback: 'ask'`（可选人工通道）启用时生效；默认 `fallback: 'reject'`，无人工通道（对齐 codex）。启用后人工无响应 → 自动 `rejected`。
- 两者默认值需给理由（人工超时默认 300000 ms：按实测人工响应 3.1–162.8 s 的样本取上界约 1.8 倍）；`0`/负值语义、与 `req.signal` 的关系、超时后的用户可见后果，都要写清并实现。

### R4 UI
- **审批卡片**：卡片本体与「拒绝 / 允许一次」两个按钮仍由宿主原生渲染；插件在卡片内注册 `conversation.approval.detail`，渲染自动审批状态行（R12）与倒计时（R13），并把原生要显示的关联命令原样渲染出来，保证非接管预设下的观感不变。
- **触发命令与审查结论**：经 `agent.inject()` 写入会话页（默认放行与拒绝都写，见 §5），包含触发的工具与命令、结论、风险与理由。
- **插件设置面**（落点、键、入口与"打开即见"判据以 R27 为准，外观与保存交互以 R29 为准；读写走 `configForms`，宿主行 id 即设置命名空间 `approve-for-me`）：审查模型选择、两条超时、模式与规则表、生效值（直接显示在控件里）与覆盖回退（「已覆盖」＋「恢复默认」，见 R29）。字段与控件不因 0.1.7 迁移增删；新增字段以 R28（两个语言开关）为准；文案按 R17/R28 支持中英切换。
- 宿主行 `Config` 的每个可编辑字段必须声明为**可热改**（schemastery 的 `.volatile()`），否则 0.1.7 的设置接口会跳过整行、写入直接报错（`@deepseek-ai/dsh-settings@0.1.7-rc.1` 的 `describe()` 只投影含 volatile 字段的行，写入对没有 volatile 字段的行抛 `Plugin entry "<ns>" has no volatile fields`）。
- 设置面仅在 loopback 页面渲染（非 loopback 入口下宿主把设置判为进程内不可持久化、设置镜像初值即为 `unavailable`，插件表单不会注册）；读不到宿主设置镜像时必须优雅降级（不报错、不影响审批功能），配置仍可通过 profile patch 本行 `config:` 生效（0.1.7 的设置值住在 profile 的 `cordis.patch.yml`）。

### R5 审计
- 每个请求一行：请求 id / 工具 / callId / 阶段 / 决策 / 使用模型 / 耗时 / 原因。
- 落点写 stderr，不得写 stdout（服务方式托管时 stdout 常被重定向成实例自身的凭据/URL 文件，写 stdout 会污染它）。
- 审查提示词与原始输出需可追溯（截断策略明确）。

### R6 路径语义
自动放行、审查拒绝、审查超时/失败、取消（abort）、可选人工通道超时——每条都要有明确的返回值与用户可见后果，并说明注入给主模型的文本。

### R7 安全边界
- 规则强制拒绝清单只保留**不可逆的极危险操作**；显式配置该清单时命中即直接拒绝，不消耗 LLM 调用，LLM 也不能推翻该拒绝（R51：出厂默认留空，清单由用户显式配置，出厂参考清单见 README）。
- 默认自动放行上限为 `danger-full-access`（见「已确定的设计决策」）；安全由 LLM 审查主担，显式配置的可选规则清单承担不可逆极危险操作的确定性拦截（R51 后口径）。
- LLM 审查只决定"是否批准这一次升权"，不改变沙箱语义。
- 会话策略 `never` 时审批服务在 waterfall 分发之前直接返回拒绝、插件不会被调用（`@deepseek-ai/dsh-user-approval@0.1.7-rc.1` 的 `decide()` 短路），不得绕过。
- 审查器崩溃 / 挂起 / 输出幻觉 → 直接拒绝（fail-closed）。
- **拒绝原因必须经 `agent.inject()` 注入会话**，让主模型看到具体理由，不能只留 dsh 的固定文案。

### R8 测试
- 单元：规则预筛、模型解析顺序、超时竞速、输出解析（含畸形）、审计格式化。
- 端到端（必须做，且要截图留档）：真实触发一次升权审批，观察规则预筛 → LLM 审查 → 自动放行；构造应被拒绝的操作，观察交人工；把 `human.timeoutMs` 调小，观察超时自动拒绝；设置面改审查模型并观察生效（loopback 入口）。

### R9 部署与回滚
- 不修改 dsh 自身 npm 包；插件只放 profile（以 ESM 包形式装进 profile 的 `node_modules`，包名列入 profile `package.json` 的 `dsh.profile.bundles`，包内 `cordis.patch.yml` 用 `- insert` 插入插件行——`@deepseek-ai/dsh-app-boot@0.1.7-rc.1` 的插件装载机制）。
- 重启不得在服务进程树内执行 `Restart-Service` 一类的自重启（服务管理器默认连整棵进程树一起杀，树内自重启会把服务停在 STOPPED，还会连带杀掉树内的其它进程与在跑的工具调用），须从服务外部重启。
- **装包即行**：安装动作（`dsh plugin add`）必须让全部功能出现，不得要求部署方手工编辑 `cordis.patch.yml` 或 `package.json`。插件自带的 bundle patch 提供 `approve-for-me` 行；`permission` 行里的「自动审批」预设条目由插件自带的部署脚本写入（幂等、可撤销）。
- **删包即净**：卸载后部署方配置里不得留下只有本插件才懂的条目。专门一条零依赖的备用清理命令负责从 profile 的 `cordis.patch.yml` 里回收「自动审批」预设条目——`dsh plugin remove` 是另一个进程，本插件的 `apply` 与 disposer 都不会执行（见 R26）。

### R10 超时提示要说清「这是超时」
- 因**超时**结束的审批（审查超时、人工超时、排队超时），注入给主模型的文本必须点明「未在时限内得到结论，本次按拒绝处理」，并说明**可以直接重试**（超时不是安全判定结论）。
- 不得只给「不要用等价手段绕过该拒绝」这类通用拒绝文案：那会让主模型以为操作被判定为危险，从而放弃重试或绕路。
- 因**判定为危险**而拒绝的路径沿用 codex 的拒绝文案（R1 的决策映射）；语言按 R28 切换：英文侧取 codex 原文，中文侧沿用现行译文。

### R11 审查期间是否弹出人工卡片，可配置
- 新增配置：自动审批状态下、审查器仍在审查时，是否弹出原生人工审批卡片。
- 开启（默认）：表现为现状——卡片在审查期间就出现，用户可抢先决定，人工结论优先于审查结论。
- 关闭：审查期间不出现卡片；仅在审查未放行且「审查未放行处置 = 交人工」时才弹出，卡片上标明结束原因是超时还是拒绝。

### R12 人工卡片必须标明自动审批状态
- 卡片内显示当前处于哪种自动审批状态：正在自动审批、自动审批超时、自动审批拒绝。
- 自动审批拒绝时，必须把审查器给出的拒绝原因一并显示。
- 状态与原因来自宿主侧的真实状态，不得由客户端推测。

### R13 人工卡片必须带自动拒绝倒计时
- 卡片内显示「还有多久会自动拒绝」，并在剩余时间内持续更新。
- 倒计时只在确实存在自动拒绝时限时显示（交人工且有 `human.timeoutMs`）。
- 没有时限（`human.timeoutMs = 0` 或当前不是交人工路径）时不显示倒计时，而显示对应的实际语义。

### R14 会话级审查模型在会话开始前就能设置
- 会话尚未激活（宿主里找不到该会话）时，不得用「会话未激活，请先发一条消息」这类提示阻止修改。
- 只要客户端已经有会话 id，就允许读写该会话的审查模型设置；写入的选择必须在会话真正开始后生效。
- 会话 id 都取不到时（尚无会话）不渲染该控件——此时没有可写入的会话键；全局默认审查模型在设置面里配置。

### R15 会话级控件只在自动审批模式下显示
- composer 的审查模型控件只在当前会话确实由本插件接管（权限预设命中 `trigger.presets`）时显示。
- 其他预设下不显示，避免与原生审批行为无关的控件长期占位。
- 判定用宿主侧结论，不在客户端猜。

### R16 接管预设改为多选下拉
- 设置面的「接管预设」不得用文本输入：用户通常不知道预设的英文 id。
- 改为多选下拉，选项来自宿主当前的预设目录（id + 展示名 + 说明），并标出当前默认预设。
- 配置里存在但目录里没有的预设 id 要显式提示（可能是预设已被移除或拼写错误），不得静默丢弃。

### R17 文案取值口径
- **语言**：用户可见文案与 Agent 提示词各自独立切换中英文，规则与默认值见 R28（用户文案默认 `auto`，观感与现状一致）。
- 值本身来自外部来源的（模型引用 `provider/model`、宿主预设的展示名与说明、工具名）保持原样：这些是数据，不是文案。
- 少数必须靠英文 id 才能核对的字段，当前语言的文案后附原值。

### R18 自动审批必须成为轨迹里可查的一等记录（**部分达成：插件自有视图已达成；记录表原生记录未达成，已移交上游**）
- **已达成**：会话「审查记录」页签给出每次自动审批的完整详情——审查提示词、送审输入、审查器思维链、最终输出（判定与理由），以及**这次审批自己的耗时**。
- **未达成（不在本插件交付范围，见 R20）**：记录表里那一条原生「自动审批」记录，以及它的位置（应在「助手（发起该次工具调用）」与「工具（该次调用）」之间）。缺的是「在宿主组装记录表时按 `callId` 关联」这一步，属宿主内部逻辑，插件侧无接缝。
- 未达成部分**必须让用户看得见**（已知局限写入 `README.md`），不得静默缺失或伪造。

### R19 工具调用时长必须与审批时长分开
- 时长条里「工具」那一段只显示**净执行时长**；审批单独成段，长度等于审批耗时。
- 拿不到分段时，界面必须在别处给出对照（「工具总计 X = 执行 Y + 审批 Z」），不允许让失真的数字单独存在。

### R20 轨迹集成只做插件自有视图
- 本插件**不改动宿主任何文件**，也不寻求以源码补丁扩展宿主。记录表原生审批记录的缺口**不属于本插件的交付**，只作为上游功能请求提出。
- 插件自有视图必须独立可用且信息不缺：审查详情（提示词 / 送审输入 / 思维链 / 输出）、每轮耗时对照（`工具总计 X = 执行 Y + 审批 Z`）。
- **做不到的功能必须如实降级并让用户看得见**（见 R18），不得静默缺失或伪造。

### R21 权限切换后控件显隐不得有可感知延迟
- 在接管预设与非接管预设之间切换时，composer 上审查模型控件的出现与消失必须即时（目标：一次本地 RPC 往返，亚秒级），不得依赖固定间隔轮询。

### R22 审查详情的采集与体积约束
- 提示词 / 送审输入 / 思维链 / 输出属敏感内容：**默认不采集全文**；开启后按条数与字节上限截断，沿用既有脱敏清单，越界留痕。
- 字段与开关语义对齐社区口径：OpenTelemetry GenAI 的「敏感内容 opt-in + 截断 + `truncated` 标记」，以及 hermes-otel 的 approval span 字段（`callId` 关联、`choice`/`outcome`、`duration_ms`、命令按预览截断）。

### R24 自动审批覆盖子代理（委派子会话）
委派机制给每个子代理会话钉死 `approval/policy=never`（`@deepseek-ai/dsh-subagent@0.1.7-rc.1` 的子会话创建逻辑：注释明说「pinned to 'never' regardless of the parent」），其升权请求在审批服务里被短路拒绝，插件的 LLM 审查根本看不到——子代理撞沙箱时只能拿到毫秒级的机器拒绝，没有任何审查与解释。本需求把自动审批扩展到子代理。

- **（不可裁剪）同一审查**：被覆盖子代理的升权请求走与主会话**完全相同**的调用链——规则预筛、LLM 审查、fail-closed、审计行、注入文案直达发起子代理本人（`request.agent`）。
- **（不可裁剪）接管判定不依赖子会话预设名**：子会话没有可命中 `trigger.presets` 的预设（实测形态为推导成 custom 或 danger-full-access），必须新增不依赖预设名的判定分支。
- **（不可裁剪）不破坏委派沙箱**：只允许追加 `approval/policy=ask` 事件；**禁止**用 `permissionPresets.set` 之类整预设写入（会连沙箱一起改写，例如把委派的 danger-full-access 降级回 workspace-write）。
- **（不可裁剪）监听器永不抛**：`session/created` 监听器抛异常会回滚宿主的会话挂载（`@deepseek-ai/dsh-session@0.1.7-rc.1` 的 enter/announce 契约注释：「a throwing session/created listener rolls the attach back instead of leaking it」），任何内部错误只能写审计，不得外抛。
- **覆盖范围按根会话预设判定**：子代理（含多层嵌套）在其**委派链根会话**的权限预设命中 `trigger.presets` 时才被覆盖；根不可判定或不在名单内 → 不覆盖（保持现状：never 自动拒绝）。
- **子代理无人工通道**：不弹人工卡、不 `next()`、不交人工；`fallback='ask'` 对子代理请求一律按拒绝结算（无头会话没有可交互的应答者，交人工等于挂起）。
- **配置开关**：`trigger.subagents: 'review' | 'skip'`，默认 `review`；`skip` 时行为与现状完全一致。
- **已知语义（接受）**：停止覆盖（改 `skip` 或禁用插件）**不撤销**已写入子会话日志的 `ask` 事件；此后子代理升权将落给下一个应答者（无应答者则 fail-closed），不回滚成 never。
- **审计**：覆盖判定与跳过各写一行（复用 `phase=screen` 的 `action=review|skip`，`preset` 字段写 `subagent` 或根预设名，`reason` 说明依据）。

### R30 毫秒字段显示秒数换算，草稿随输入实时更新（不可裁剪）
设置面上以毫秒为单位的两个字段——审查超时（`reviewer.timeoutMs`，本机部署的迁移值 `300000`；出厂默认见 README）与人工超时（`human.timeoutMs`，本机部署的迁移值 `600000`；出厂默认见 README）——读到的就是一串六位数字，量级要心算。本条要求把量级直接显示出来：**生效值**换算成秒常驻显示，**正在输入的草稿值**也换算成秒并随敲键实时变化。换算只是显示层——配置、profile patch、审计行（`ms=31228`）与按字节核对的注入文本一律不变。落点是该字段的说明带：这两个字段都由官方组件渲染、它的说明是**单串** `hint`，而官方组件在字段非法时只渲染非法文案、`hint` 整段被顶掉（`@deepseek-ai/dsh-client-ui-primitives@0.1.7-rc.1` 的 `SettingsValueField` 消息段互斥：`props.invalid ? props.invalidLabel : props.hint`），因此换算读数**必须自绘一行**、紧随该字段的说明或非法文案之后（**不得**拼进官方组件的 `hint`，否则非数字输入期间生效值读数会消失）。

- **（不可裁剪）两个读数都要在**：①**生效值**换算常驻——显示当前生效毫秒值对应的秒数，不随草稿变化；②**草稿**换算实时——按输入框里的当前文本换算，每次输入后**立即**更新，不得防抖、不得等失焦、不得等保存，也不得只在保存后刷新。
- **（不可裁剪）换算与写法**：秒 ＝ 毫秒 ÷ 1000；整数不带小数点（`300000` → `300 秒`），非整数最多一位小数（`1500` → `1.5 秒`）；`0` 照数字面显示 `0 秒`——换算区**不写**「不限时」「立即拒绝」这类语义判断（两个字段的 0 语义不同，语义仍由字段名与说明承担）；不得把秒数回写进配置。
- **（不可裁剪）空值、非法值与「恢复默认」的姿态**：草稿为空或不是合法数字时，草稿读数显示占位（`—`）；「合法数字」与 `fromDraft` 的校验同一口径——有限、`≥ 0`、**整数**（`12x`、`-1`、`1.5` 都算非法）；不得沿用上一个合法值的秒数，也不得整段隐藏——**生效值那一行始终在场**（含草稿非法期间）。点「恢复默认」后控件显示的是组合层默认值，草稿读数按该文本换算（与控件显示一致），生效值读数仍是快照里的生效值。
- **（不可裁剪）双语与文案**：换算文案进字典（R28 的中英键集一一对应断言会核），单位跟随字段说明的语言——中文 `300 秒`、英文 `300 s`（数字与单位之间一个半角空格）；数字用半角。读数文案**不得含「当前生效值」四字**（R29 的退役件零命中断言守着，见 `test/settings-dom-dump.test.mjs`）。
- **适用范围**：以毫秒为单位的数值字段。现行设置面＝审查超时与人工超时两个；将来把别的 ms 字段（并发排队超时、熔断冷却）暴露到设置面时一并适用。字节与令牌类字段（输出上限、注入字节上限）**不**做换算。
- **判据（本包页面 DOM，可失败）**：①打开本包页面，两个 ms 字段的生效值换算读数与当前生效值一致（本机部署迁移值读数示例：审查超时 `300000` → `300 秒`、人工超时 `600000` → `600 秒`）；②在输入框里键入 `120000`（**不保存**），同一次输入后该字段说明带即出现 `120 秒`，而生效值读数仍是 `300 秒`；③输入 `1500` → `1.5 秒`；④清空输入 → 草稿读数为占位、生效值读数不变；⑤保存 `120000` 后重开本包页面，生效值读数变 `120 秒`；⑥切到 `en` 档后单位变 `s`；⑦输入 `12x`（非数字）→ 草稿读数为占位、**生效值读数仍在场**。变异验证：把草稿读数改成只在保存后更新 → ②红；把占位改成沿用上一个合法值 → ④红；把生效值读数拼进官方组件的 `hint` 单串（非数字输入时随 `hint` 被非法文案顶掉）→ ⑦红；把秒数写回配置（保存后 patch 里出现秒数而非毫秒）→ 配置回读断言或 ⑤ 红。

### R31 审查结论的复用边界：键不塌缩、失败不复用、缓存有界（不可裁剪）

并发去重以 `会话 id + callId` 为键（`lib/scheduler.js:131`）。审批请求的 `callId` 是可选字段，`lib/index.js:66` 直接取 `request?.callId`，缺省即 undefined，键塌缩成同一形态（`会话:-`）——同会话内两个都缺 callId 的请求共用一条审查结论，第二个请求不再审查、直接拿第一个的判定（放行或拒绝都可能）。两处生命周期缺陷同源：①失败结果也进 60 秒 TTL 缓存——排队超时、熔断开启、任务错误同样写进 `dedupe.set(dedupeKey, { at, result })`（`lib/scheduler.js:152-155`），失败后 60 秒内的重试拿到的是缓存里的旧失败，而不是一次新审查；②过期清除只发生在**同一键**再次请求时（`:133-137`），callId 每次工具调用都不同，绝大多数条目无人再访，Map 只增不减（scheduler 内对该 Map 的删除只有同键重访一处 `:136`；库内其余 `.delete`/`.clear` 都落在别的结构上——如 model-resolver 的容量淘汰 `lib/model-resolver.js:255`、pending-state 的桶清理 `lib/pending-state.js:78-79`——没有一条清 dedupe 的异键条目）。

- **（不可裁剪）缺 callId 不得共享结论**：无法证明「同一物理请求的重复投递」时，一律按独立请求处理——各自触发审查。请求级随机 id 参与键拼装是现成先例（gate 的 pending 键，`lib/gate.js:123`）。
- **（不可裁剪）失败结果不得进 TTL 缓存**：只有拿到终态审查判定（放行/拒绝类 verdict）才可缓存复用；排队超时、熔断开启、任务错误一类失败在下一次请求时必须重新走完整流程。
- **（不可裁剪）缓存有界**：dedupe Map 设条目上限，超限按最旧淘汰（或等价的定期清扫）；上限值写成常量并注释量级依据。
- **姿态**：修的是「复用」边界，不是删掉去重——同 callId 的并发竞速仍然必须只触发一次审查，既有并发语义不变（回归用例钉住）。
- **判据（单测注入，可失败）**：①同会话两个缺 callId 的请求并发到达 → 审查器调用计数 = 2（修复前第二请求复用第一请求结论，计数 = 1）；②一次 queue-timeout 失败后立即重发同一 callId → 调度执行计数 = 2（修复前直接拿缓存失败，不执行）；③连续 2000 次不同 callId 后读内部 Map 尺寸 ≤ 上限（修复前线性涨到 2000）。变异验证：把键改回塌缩形态 → ①红；失败结果重新入缓存 → ②红；去掉淘汰 → ③红。

### R32 grep 的资源上限与同步执行防护（不可裁剪）

审查器把模型给出的 pattern 直接 `new RegExp(args.pattern, 'u')`（`lib/readonly-tools.js:384`），对每个候选文件**整读入内存**（`:406`，无 stat 预检、无大小上限——对照 read_file 的有界读取 `:140`），再逐行**同步** `regex.test`（`:412-417`；行字符上限只限行长，不限回溯）；目录模式的候选文件数无上限（`:430-437`，`WALK_MAX_DIRS=4000` 只限目录数）。三个后果：灾难性回溯 pattern 冻结事件循环——`withTimeout`（`:216`）的 setTimeout 回调在同步执行期间无法触发，R1b 承诺的单工具超时在 grep 路径形同虚设；超大文件整读撑内存；候选无上限拖长审查。只读工具的输出会拼进发往外部 LLM 供应商的提示词，这条同时是安全面：被审会话可以借恶意 pattern 或巨型文件拖死审批。

- **（不可裁剪）文件大小上限**：读文件前 stat 预检，超阈值跳过该文件并在结果文本里说明跳过了哪些超大文件；跳过不得中断其余候选。阈值进常量或配置（1 MiB 量级起步）。
- **（不可裁剪）候选文件数上限**：目录模式收集候选时设上限，超限停止收集并在结果里说明截断数量。
- **（不可裁剪）同步正则的时间上界**：模型 pattern 的执行不得能无限占用事件循环——静态校验拒止病态形态（无界嵌套量词一类），或把匹配移进可强制终止的执行环境；实现方式属设计题（§3 问题 10），但「超时回调必须可触发」是强制约束。
- **判据（单测注入，可失败）**：①对超过阈值的文件 grep → 结果含跳过说明、同目录小文件仍命中（对照）；②目录含超上限个候选 → 结果说明截断；③病态 pattern（嵌套量词 + 长全 a 行）→ 在 toolTimeoutMs 内返回错误或超时结果、审计 `phase=tool` 行照写（修复前事件循环冻结、超时失效）。对照：正常 pattern 的既有用例全部保持。变异验证：去掉 stat 预检 → ①红；去掉候选上限 → ②红；匹配改回无防护同步 → ③红。

### R36 审查器工具的热改接线：脱敏清单与单工具超时（不可裁剪）

`createReadonlyTools` 在 `apply()` 时一次性快照两个生效值：`timeoutMs: current()?.reviewer?.toolTimeoutMs` 与 `redactPatterns: current()?.context?.redactPatterns`（`lib/index.js:284-290`），readonly-tools 闭包固化（`:197-198`、`:216`、`:220`）。后果一：`toolTimeoutMs` 在 schema 声明 `.volatile()`（`lib/config.js:77`），按 R4 的 volatile 语义应热改生效，实际永不生效——把它从 5000 改成 60000 后，下一次审查的工具仍在 5 秒被掐断、按「无证据」偏保守处理，且无任何提示。后果二：`redactPatterns` 未标 volatile，但注入路径（`lib/index.js:162` 现读）与记录路径（`:201` 现读，注释明言模式热改无需重建）都按**现读**实现——同一份清单三条消费路径两种口径，工具结果路径按旧清单漏到插件重挂为止。同文件有正确先例：`setRoot`/`setLang` 每次请求现设（`lib/index.js:62-64`）。

- **（不可裁剪）单工具超时按次生效**：审查前现设（`setToolTimeoutMs` 与 `setRoot` 同形），或构造参数改传读取函数；热改后**下一次审查**即按新值。
- **（不可裁剪）脱敏清单三路同口径**：工具结果、注入、记录三条路径对 redactPatterns 全部现读；schema 侧是否随之补 `.volatile()` 标注（volatile 解包机制对数组字段的适用性）在设计阶段核。
- **（不可裁剪）一致性守卫**：一条断言测试钉住「三路同时生效」——改清单后三路在同一时点之后行为一致。
- **判据（单测注入，可失败）**：①不重挂载把 `toolTimeoutMs` 5000→60000，触发必然超时的工具调用 → 审计 `phase=tool` 行 ms 接近 60000（修复前停在 5000 左右）；②挂载后追加 redact 模式，grep 命中新形态密钥 → 工具结果被遮蔽（修复前仍外漏）、注入路径遮蔽保持（对照）；③一致性守卫在盘。变异验证：接线改回构造期快照 → ①②③红。

### R37 数值配置字段的边界校验（不可裁剪）

毫秒字段全部 `z.natural()` 声明、无上限（`lib/config.js:66,77,83,109,121`——`natural()` 只保证非负整数）。Node 的 `setTimeout` 对大于 2147483647 的延时按 1ms 处理，而 `rt.timer` 是裸 setTimeout（`lib/index.js:93-101`）、gate 与排队侧直传配置值——手写 patch 多打几个 9（或误把微秒当毫秒），加载不报错，之后**每次审批在毫秒级按 review timeout 拒绝**，reason 显示「审查超时」，现象与配置意图完全相反且有误导性。另一处：`temperature` 是唯一 `z.number()` 数值字段（`:73`），无范围与 NaN 防护，负值/NaN 直送审查请求。R3 只规定了 0 与负值的语义，上限与范围无处规定；schema 数值边界目前零直接用例（并见 R44）。

- **（不可裁剪）毫秒字段上限**：schema 层给出 `max`（技术上界 2147483647；是否给更紧的业务上限留设计）；超限值**拒绝加载且报错可见**（与负值同姿态）——若实现选「钳制 + 审计留痕」也接受，但必须二选一显式，不得静默。
- **（不可裁剪）temperature 范围**：`min(0).max(2)`（或与服务商约定的范围），NaN 显式拒绝。
- **（不可裁剪）边界直接用例**：2147483647 通过 / 2147483648 拒绝；0 通过（语义按 R3 不变）/ -1 拒绝；temperature 边界同口径。
- **判据（配置注入，可失败）**：①配 `reviewer.timeoutMs: 2147483648` → 加载失败报错可见（或按所选口径钳制并留审计行），且审批不会毫秒级 timeout；②配 `temperature: -1` → 拒绝；`.nan` → 拒绝；③边界用例在盘。变异验证：去掉 max → ①③红；去掉 temperature 约束 → ②红。

### R38 计时器与中止回调的抛错防御（不可裁剪）

`rt.timer` 的回调里直接 `settle(value)`（`lib/index.js:93-101`）——onFire 抛错时 settle(undefined)，返回值位移被当成「正常结算值错误」处理，错误来源被伪装（gate 侧 mismatch→invalid 走向，`lib/gate.js:261,263`）；中止监听 `() => settle(onFire())` 同样无保护（`lib/index.js:117-119`）。方向悖论：本插件的总前提是超时、解析、模型失败一律按拒绝方向结算，onFire 抛错本应同律，修复前却变成语义漂移的 invalid 结算。

- **（不可裁剪）onFire 抛错按本义结算**：timer 侧按超时语义、abort 侧按取消语义结算为拒绝方向，reason 指明「计时回调抛错」；不得以 undefined 值位移。
- **（不可裁剪）不得产生进程级未捕获异常**（uncaughtException）。
- **（不可裁剪）两处回调同口径**：timer 回调与 abort 监听同一条防御。
- **判据（单测注入，可失败）**：①注入 onFire 抛错的 timer → 结算为拒绝语义、审计 reason 含计时回调抛错说明（修复前 TypeError 位移）；②已中止 signal + 抛错的 onAbort 回调 → 结算为取消语义、进程无未捕获异常。变异验证：去掉防御 → ①红且②出现未捕获。

### R39 迟到审查结论的观测口径（不可裁剪）

gate 结算（超时/取消/人工）后，审查流的 `finish()` 仍**无条件**写审计行与 onReview、并继续持有并发位到审查流自然结束（`lib/reviewer.js:329-368`）——迟到结论没有任何「已结算」感知：审计里 `phase=review decision=allow` 照写，观测面分不清「按时结论」与「超时后才到的结论」，复盘时会误读为「明明放行了却按超时拒绝」。迟到结论不会二次注入（deliver 只在 gate 结算路径上调用），但这一点目前没有任何测试钉住（并见 R44）。

- **（不可裁剪）迟到结论可辨识**：gate 已结算后到达的 finish 写的审计行带明确标记（abandoned 类字段或独立 reason 措辞），观测面能区分按时/迟到。
- **（不可裁剪）不重复注入、不改写结算**：迟到结论不得再注入主模型、不得改写已结算结果——用常驻断言钉住（等待迟到 finish 完成后核对注入次数恰 1、decide 行恰 1）。
- **（不可裁剪）并发位不悬置**：gate 结算即中止审查流（signal），finish 后并发位立即释放的时点要有断言——迟到流不得在队列里压住后续审查。
- **判据（单测注入，可失败）**：审查时长大于超时、放行结论迟到 → 审计出现带迟到标记的 review 行；注入次数恰 1；decide 行恰 1；后续审查不被压住。变异验证：删掉标记 → 观测断言红；让迟到路径改写结算或再注入 → 常驻断言红。

screen() 的三类跳过——委派模式 off、工具名不在 `trigger.tools`、非升权请求——直接 return，不写任何审计行（`lib/policy.js:123-140`；gate 透传 `lib/gate.js:168,176-178`）。R5 承诺「每个请求一行」，三径缺位意味着接管范围变化后无法从 stderr 复盘哪些请求被规则放过、哪些根本没进审查。preset 覆盖的 skip 已有审计先例（`lib/mode.js` 的 auditSkip，含 `trigger.auditEverySkip` 开关）。

### R46 审查通道故障的注入文案与拒绝分离（不可裁剪）

审查结论为 `error`（LLM 流失败、空输出、截断、模型不可用、`queue-overflow`、`breaker-open`、插件内部异常）时，注入给主模型的文本沿用**拒绝模板**——末句是 codex `REJECTION_INSTRUCTIONS`（「不要用等价手段绕过该拒绝……」；`lib/gate.js:311-318` 的非 `timedOut` 分支调 `rejectText`，内部异常 catch 分支同款）。实测后果（2026-09-28 实机会话：三次供应商侧 `INVALID_REQUEST` 故障全部被注入拒绝文案）：主模型把「审查器自身故障、无结论」读成「判定为危险、不许绕过」，可放行的操作被误拒后不能自愈，需用户明确指示才敢原样重发；无头会话没有这个出口，且会被推向不经审批的降级绕行。R10 已为**超时**确立「不是安全判定要说清、可直接重试」的口径，本条把同一口径延伸到 `error` 判定。

- **（不可裁剪）error 与 deny 分文案**：`deny` 判定（LLM 给出 `outcome:'deny'`、规则命中、升权超上限）继续用拒绝模板，末句不变；`error` 判定改用**通道故障模板**——点明「自动审查通道故障、未得出安全结论」、带故障原因、说明同一操作可直接重试（重试会重新发起一次自动审查）。`REJECTION_INSTRUCTIONS` 末句只保留在 deny 路径。
- **（不可裁剪）三文案选择集中**：超时（`timedOut=true`，R10）/ deny / error 三种文案的选择逻辑集中在 gate 的结算分支；`queue-overflow`、`breaker-open`、内部异常同样走通道故障模板。
- **（不可裁剪）防重试风暴指引**：通道故障模板必须带「重试仍失败则停止连续重试、把故障报告用户」的指引（与超时模板末行同款句式），不得写成无限重试许可。
- **（不可裁剪）文案纪律随 R28**：新模板进 `lib/agent-texts.js`（zh/en 键集相等断言自动覆盖新键）；en 档结构与 zh 一致、首行 `[approve-for-me] ` 前缀；结算仍 fail-closed（`rejected`）——本条只改注入语义，不改返回值、不改 `ui.inject` 三档判定、不改卡片三态。
- **判据（单测注入，可失败）**：①审查流抛错（`decision='error'`）→ 注入文本含通道故障标识与「可以直接重试」，**不含**「不要用等价手段绕过该拒绝」；②deny 判定 → 注入末句仍是 codex 原句（回归）；③超时 → 超时文案不变（回归）；④`queue-overflow`/`breaker-open` → 同①；⑤zh/en 键集相等断言覆盖新键。变异验证：error 分支改回 `rejectText` → ①④红；新键从任一语言删掉 → ⑤红。

### R47 审查调用的有限重试（不可裁剪）

审查器对 LLM 流的失败**零重试**：一次网络抖动、空响应或供应商侧错误就直接落 `error` 判定（`lib/reviewer.js:212-316` 的循环只迭代工具轮次，`catch` 即终局；设计 §7.1 明文「本插件不做自动重试」）。实测三次 `INVALID_REQUEST` 故障中，可证的同命令重发即恢复（用户指示重试后 89 秒放行）——瞬时故障全部推给主模型重试，意味着每次抖动都先吃一次误拒注入。codex 先例是 3 次尝试共享同一 deadline（§7.1 所引 openai/codex `ext/guardian-reviewer/src/lib.rs:31` 上下文）。

- **（不可裁剪）按错误类重试**：可重试类——流抛错（网络/供应商异常）、宿主 `finish.kind='error'`（含 `INVALID_REQUEST`、`EMPTY_RESPONSE`；实测显示该类错误同样间歇出现，按可重试处理）、空输出（无文本块且非截断）；不可重试类——`output-truncated`（同参数必然复现）、`layer=unavailable`（模型解析失败，确定性）、审查器装配错误。判据写成单一谓词并导出供单测。
- **（不可裁剪）次数有界、预算不外溢**：尝试总次数进具名常量（首次 + 1 次重试）并注释量级依据；重试消耗的时长计入 `reviewer.timeoutMs` 同一预算——gate 的审查计时器先到仍按超时结算（R10 语义优先），`reviewer.timeoutMs = 0` 时仅以次数为上界。
- **（不可裁剪）整建重试**：重试从同一 system/输入整建请求，不复用已抛错轮次的残缺消息序列；审查请求仍不带 `sessionId`。
- **（不可裁剪）重试留痕**：最终审计 review 行的 reason 标明尝试进度（如 `attempt 2/2`）；trace 记录按请求一份，不因重试翻倍；注入给主模型的原因同样带尝试进度。
- **判据（单测注入，可失败）**：①llm 替身第一次抛网络错、第二次成功 → 最终判定取第二次（修复前直接 error）；②连续失败达上限 → error 判定且审计 reason 含尝试进度；③`reviewer.timeoutMs` 小于「首次失败耗时＋重试耗时」→ 按超时结算（不是 error）；④`output-truncated` 与 `layer=unavailable` → 零重试。变异验证：去掉重试 → ①红；次数上限放开 → ②红；重试绕过预算 → ③红。

### R48 error 计入熔断窗口（不可裁剪）

熔断器只统计 `allow`/`deny`（`lib/scheduler.js:75-85` 的 `record`：`:76` 对其余 decision 直接 return），`error` 连发既不累计 `consecutive` 也不进 `window`——审查模型持续故障时，每个新请求都完整烧一轮注定失败的 LLM 调用（最长达 `reviewer.timeoutMs`），然后被注入「判定为危险」文案（R46 前的现状）。R47 引入插件内重试后，故障期的调用量再乘以尝试次数，无熔断的浪费被放大。

- **（不可裁剪）error 计数**：`record` 把 `error` 与 `deny` 同权计入 `consecutive` 与 `window`；`allow` 清零 `consecutive` 的语义保持；熔断打开条件、冷却时长、窗口参数（`breaker.*` 现值）不变。
- **（不可裁剪）调度失败不计数**：`queue-overflow` 不是审查结论（并发占满），计数会把并发高峰误读成通道故障；`breaker-open` 期间零审查，自身也不计数。
- **（不可裁剪）观测口径不合并**：审计与 `state()` 快照里 `error` 与 `deny` 仍可分辨（decision 字段分开），计数口径的改变不抹平两者的观测区别。
- **判据（单测注入，可失败）**：①连续 error 达 `consecutiveDenials` → 熔断打开，下一请求零 LLM 调用直接 `breaker-open`；②error、error、allow、error、error → 未打开（清零语义保持）；③deny 连发熔断打开的既有用例回归不变；④构造 `queue-overflow` → 熔断计数不变。变异验证：`record` 对 error 继续 return → ①红。

## 5. 已确定的设计决策

| 项 | 决定 | 理由 |
|---|---|---|
| 自动审批的形态 | **审批应答者**（保留沙箱 + 撞墙升权 + 逐次审查）；**明确不采用**宿主 0.1.7 的官方 `auto` 预设语义，不调 `registerAuto` | 用户裁定：继续继承 codex `--approve-for-me` 的形态。功能依据：`auto` 固定无沙箱 + `approval: never`，而 `never` 让审批在 waterfall 之前短路，应答者收不到请求（依据同 §1） |
| 预设条目与默认预设 | 「自动审批」预设条目由**插件的部署脚本**写入/回收 profile patch；`permission.defaultPreset` **不得**取插件预设名；该预设必须与 `workspace-write` 取值相同且声明在其后 | R26：条目靠部署方手写就违反「装上就出现、卸下就消失」；预设名进了跨会话记忆，插件不在场时就是空壳。排序依据：同组合按声明顺序取第一个匹配项（`@deepseek-ai/dsh-permission-presets@0.1.7-rc.1` 的 `derive()`） |
| 默认自动放行上限 | 允许到 `danger-full-access`（不因模式上限拦截） | 依据：默认 `workspace-write` 会话下唯一升权目标就是 `danger-full-access`（宿主 `@deepseek-ai/dsh-sandbox@0.1.7-rc.1` lib/index.js 的 `WIDER_MODES` 组合；实测升权 reason 全部指向该目标），若默认拦截则自动放行率恒为 0、插件失去意义；对齐 codex approve-for-me 会批准 escalated permission。安全由 LLM 审查主担，显式配置的可选规则清单承担确定性拦截（R51 后口径） |
| 审查拒绝后的处置 | `deny` → **直接拒绝**（不交人工），并注入拒绝原因 | 对齐 codex（`core/src/tools/approvals.rs` 的 `Denied → ToolError::Rejected`）；用户明确取消"打回后再交人工复核" |
| 人工通道 | 默认关闭（`fallback: 'reject'`）；`'ask'` 为可选项，启用时才用 `human.timeoutMs` 超时拒绝 | 对齐 codex 的无人工通道；保留可选通道以兼容无人值守场景 |
| `human.timeoutMs` 默认 | 300000 ms（仅 `fallback: 'ask'` 时生效） | 实测人工响应 3.1–162.8 s，取上界约 1.8 倍 |
| 审查器工具 | 必须能自主调用**只读工具**收集证据，工具调用不得触发审批 | R1b：无人工通道时，无工具 + 保守判断会导致大量误拒 |
| 审批卡片 | 卡片与按钮保持原生；插件在卡片内注册 `conversation.approval.detail`，加一条自动审批状态行与倒计时，并把原生那条关联命令原样渲染（R12/R13） | 用户要求卡片能看出「正在自动审批 / 超时 / 拒绝」与「多久后自动拒绝」；该 seat 是 `single`（同槽只渲染一个占用者，后注册且 priority 更小者胜——宿主 slot 机制），接管后必须自己渲染命令，否则会丢掉原生的命令预览 |
| 弹卡时机 | 默认在审查期间就弹出卡片（可抢先人工决定）；`ui.humanCardDuringReview = false` 时只在交人工阶段弹出（R11） | 默认行为与现状一致；关掉可避免「审查本来会放行、卡片却先弹出来打断」的场景 |
| 审查期间的人工结论 | 人工抢先回答时以人工结论为准，审查流被中止 | 人比模型更有权威；与现状一致 |
| 会话级控件显隐 | 只在当前会话确实由插件接管时显示（R15） | 避免在「工作区内修改」等预设下出现与原生行为无关的控件 |
| 显隐的触发方式 | 订阅宿主已发布的 `permissions` 投影作为变化信号，一变化就重拉 `getState`；保留一个 10 s 备用轮询 | R21：轮询间隔是"最坏情况延迟"的直接来源（修复前 3 s）；投影是宿主现成通道，客户端只当闹钟用，接管判定仍在宿主侧 |
| 轨迹集成的形态 | 只做插件自有视图（会话「审查记录」页签 + 每轮对照），不提供任何"分档"或"打补丁"的选项 | R20：插件不改动宿主文件；记录表原生记录属宿主内部逻辑，已移交上游 |
| 审查详情默认不采集全文 | `trace.capture` 默认 `summary`；`full` 时按条数与字节上限截断、沿用脱敏清单、越界留痕 | R22：对齐 OTel GenAI 的敏感内容 opt-in 与 hermes-otel 的 preview 截断口径；提示词与思维链体量大且含敏感信息 |
| 会话页留痕 | `ui.inject` 默认 `all`：放行注入简短一行，拒绝/超时/失败注入完整三段 | 用户要求能看到“哪条命令触发 + 审查回复” |
| 会话级模型下拉（composer） | 自建 Remote 命名空间（`getState` / `setSessionModel` / `modelCatalog`）；不可用时下拉不渲染，其余功能不受影响 | 下拉需要读写会话级选择与模型目录 |
| 子代理覆盖的翻策略写法 | 只追加 `approval/policy {policy:'ask'}`（省略 `source`），在 `session/created` 监听器内同步完成 | 宿主契约：整预设写入会改写委派沙箱（R24 禁止）；`source` 字段类型只写了 `'delegation'`，自定义值可能被投影校验拒绝；监听器内可安全 `append`（挂载钩子先于事件安装），但监听器抛错会回滚会话挂载，故任何失败只写审计 |
| 子代理覆盖的判定锚点 | 委派链**根会话**的权限预设 ∈ `trigger.presets`（不是父会话、不是子会话自身） | R24：嵌套子代理的父会话没有稳定预设（custom 或继承值）；根会话一定有 `pinInitialPermission` 补记的预设事件；根不可达（跨进程/已结束未装载）则不覆盖，保持 never 的 fail-closed |
| 子代理的人工通道 | 无：不 `next()`、不弹卡、`fallback` 对子代理一律按拒绝结算 | 无头会话没有可交互的应答者；waterfall 交人工等于无限挂起（R24） |
| 设置面的外观与保存交互 | 照官方设置表单重绘：删除「重置全部覆盖」，回退覆盖改用单字段「已覆盖」＋「恢复默认」；写入时机统一为「只有保存才写」；落点仍留在 bundle 级配置槽 | 用户裁定：本包设置面与官方设置页并排看是两套样式（规格对照＝`@deepseek-ai/dsh-client-ui-primitives@0.1.7-rc.1` 的 `SettingsForm`/`SettingsValueField`）。落点不迁：槽位目录明说 bundle 的配置属于 `plugins.bundle.config`／`plugins.row.config`，`plugins.item` 是官方宿主命名空间设置页用的槽位（`@deepseek-ai/dsh-client-ui-plugin-manager@0.1.7-rc.1` 的槽位契约），R27 的落点判据不变 |
| 毫秒字段的秒数显示 | 设置面的两个毫秒字段（审查超时、人工超时）在常驻说明带显示生效值与草稿值的秒数换算，草稿随输入实时更新；存储、审计与注入文本仍用毫秒 | 用户裁定：六位毫秒数读不出量级。换算只在显示层，配置与按字节核对的证据（审计 `ms=`、`injectBytes`）不受影响；两个 ms 字段都由官方 `SettingsValueField` 渲染、说明是单串 `hint`，换算读数必须自绘一行 |
