# 公开文档原则

本文适用于公开说明和项目自有注释。其他维护文档引用本文，不另写一套相同规则。法律原文完整保留；发布历史按记录职责保留。

## 先确定读者要做什么

| 文档 | 回答的问题 |
| --- | --- |
| [中文首页](<../README.md>)与[英文首页](<../README.en.md>) | 插件做什么？能否用于当前 DSH？怎样取得安装件、安装和开始使用？ |
| [中文用户参考](<user-reference.md>)与[英文用户参考](<user-reference.en.md>) | 怎样设置、选择模型、理解审批、查记录、排障、更新和卸载？ |
| [参与指南](<../CONTRIBUTING.md>) | 怎样准备源码、修改和测试？审查、提交与发布由谁负责？ |
| [需求](<requirements.md>) | 已批准的目标、行为、默认值、边界和验收结果是什么？ |
| [设计](<design.md>) | 机制怎样工作？为什么这样处理？有哪些已知限制？验证覆盖哪些范围？ |
| [验证说明](<verification.md>) | 工具需要什么？会读写什么？需要哪些权限？怎样判断结果和清理？ |
| [变更记录](<../CHANGELOG.md>) | 每个版本改变了什么？使用者是否需要调整配置或操作？ |
| [许可](<../LICENSE>)与[来源通知](<../NOTICE>) | 可以怎样使用、修改和分发？需要保留哪些声明？ |

首页先给当前适用版本和真实安装来源，不要求安装者先读需求或维护记录。用户参考补齐完整用法。维护过程、审查安排和实现细节放在维护资料中。

## 用平实的语言讲清楚

- 一句话表达一个主要意思，一段解决一个问题。条件、动作、结果和例外分开说明。
- 使用常用词。同一概念使用同一名称，不为避免重复更换术语。
- 必须使用技术词时，就近说明用途。命令、字段、模型 ID、路径和协议标记保持准确。
- 多个动作按执行顺序编号。先写前提，再给命令，最后说明怎样确认成功。
- 面向开发者可以保留专业细节，但不用长难句压缩信息。
- 拆成列表、减少字数或移到参考页，都不能单独证明已经容易理解。

普通说明不应复述内部审查规则，也不应反复证明作者没有越界。判断每段是否保留时，问：读者看完后，哪个判断或动作会不同？没有作用的说明删除。

注释说明代码难以表达的原因，如安全边界、失败处理、协议背景和数值理由。不要逐行复述代码，也不把修复批次和制作署名写进注释。

## 简化表达，保留事实

需求记录已批准的要求。源码、配置定义和包元数据说明当前实现。出现差异时，查明并报告，不降低需求来配合实现。目标、实现、验证和发布分别说明。

改写时保留：

- 版本、参数、配置键、枚举、默认值、范围、单位和合法类型。
- 条件、必要例外、权限、失败处理、生效时点和数据保留行为。
- “可能”“建议”“通常”“计划”等确定程度。
- 跨字段关系，以及零、空串、空清单、缺席值各自的含义。
- 已批准但暂缓的要求。不能因章节重组把暂缓项写成取消或已实现。

[需求 5.3](<requirements.md#53-配置默认值>)定义批准默认值。用户参考可以按任务完整呈现这些事实。唯一权威不等于只能出现一次事实：需要同步检查，而不是让用户到需求中拼接用法。

配置表逐字段核对实现。默认值尽量使用可解析的字面量。对象、清单和脱敏形态可以给明确结构说明。固定文件数量等机制常量单列，不伪装成配置字段。不另建第三份人工默认数据表。

## 风险说明给出下一步

必要条件和风险放在相应操作之前。写清四件事：何时发生、会有什么后果、怎样确认、接着怎么办。

能给出恢复方法就给方法。需要维护者协助时，说明求助对象和应提供的脱敏信息。无法恢复但影响操作选择时，保留具体后果，让读者能决定是否继续。

保留影响使用、结果理解和安全的限制。删除无关排除和重复自证，不用“以实际为准”“后果自负”等话代替处理路径。法律免责条款按法律职责保留，不套用普通说明的删减规则。

安全提示、模型指令与普通用户说明的任务不同。不能按普通文案精简规则删除模型必须遵守的授权、安全、输出格式或失败处理指令。指定安全英文、协议、法律文本和来源声明按其精确保留要求处理。

## 两语用户资料各自完整

- 修改使用事实时，同时核对两语首页和两语用户参考。
- 两语面向同一版本，参数、默认值、风险、生效方式和恢复步骤一致。
- 英文用户不应依赖中文需求或设计来补齐正常操作。
- 两语使用自然表达，不机械逐字翻译，也不堆叠同义中英文词。
- 两份首页顶部互链，两份用户参考互链。首页链接本语言参考。
- 用户资料的必要入口限于本语言用户参考和许可资料；源码维护资料不能成为使用前提。

## 当前说明、历史与制作信息分开

需求和设计直接维护当前要求与机制。修正旧值时改为正确值，不保留相反版本和纠错流水。修订过程由 Git 保存。

变更记录保留真实发布历史、顺序和发布结论。确需澄清历史难句时，不能增加、删除或改写发布事实。版本条目直接写功能变化、使用影响和升级动作，不把本地检查说成发布完成；公开文档也不记录候选是否已发布或逐轮验收进度，临时进度留在过程问题清单。

AI 名册仅说明制作信息，不放在用户首页，不作验证或兼容结论，也不代替版权署名。

## 维护增补需求

新增要求暂时放在增补章节时，使用稳定标识，并注明所属主题。每项至少写清：

- 要解决的用户问题、适用条件和所需行为。
- 默认值、失败处理和必要例外。
- 能判断通过或失败的验收结果。

改变已有规则时，同时修正原条款，只留一套现行要求。待决定的建议不能写成已批准要求；实现与需求的差距也不能伪装成新产品要求。实现机制写入设计，修订过程由 Git 保存，不写进现行需求流水。

维护者定期把增补并入对应主题，删除已归并的重复正文。同时修正全文对增补标识的引用，不留悬空指针。未归并的 H1–H6 保留稳定标识和当前批准状态；暂缓开发不等于取消，也不等于已经实现。

## 维护资料能独立执行

准备、修改、审查、验证和发布所需的规则写在仓库内。不要求读者先安装维护者的私有技能、取得私有工单或使用某台机器的路径。

工具说明先分类风险，再给命令。至少说明：

1. 使用的源码和宿主版本、依赖与运行环境。
2. 目标选择顺序，以及执行前怎样确认目标。
3. 读取凭据、会话正文或其他私有数据的范围。
4. 网络端点、可能计费、配置或文件写入等副作用。
5. 隔离、备份、失败处理和自有资源清理方法。
6. 通过、失败、跳过和未验证各自表示什么。

只读是读写行为，不是隐私保证。会话日志读取工具仍会接触正文。浏览器驱动可以保存配置、发送消息或执行页面表达式，不能统称为只读截图工具。

## 检查源码和实际安装包

继续分发整个 `docs/`，并带上两语首页、参与指南和变更记录。运行包没有带齐源码测试和开发工具。包内维护资料提到这些文件时，用源码相对路径文字说明获取位置，不创建指向包内缺席文件的相对链接。

发布前用 `npm pack --ignore-scripts` 检查实际归档，不仅看文件清单。确认版本、入口、安装声明、两语资料、维护资料、安全策略和法律文件齐全；包内相对文件及片段链接有效。临时产物仅清理本次创建的内容。

公开用户资料应以仓库读者能够自行取得的源码和安装路径编写，不能把向维护者索取文件作为默认前提，也不记录当前私有或临时交付状态。首页默认提供直接从 GitHub 适配分支安装的可执行命令，源码目录安装与本地打包作为备用选项。备用命令自动使用当前目录或生成的安装包路径，不让读者为默认用法补填占位符；仅在确有对应发布物时使用 Release 附件、标签或包源作为安装入口。分支会继续更新，复现安装应记录实际提交或安装包校验信息。

第三方归属按固定官方证据填写。保留适用版权、许可、改写和翻译范围。不要把来源核验报告称为法律认证，也不要为了补归属改写安全正文或重新许可项目。

## 按读者任务审查

先完整阅读，再运行自动检查。审查者按目标读者的知识判断，不用自己掌握的实现细节替文档补空白。

| 任务 | 应能确认什么 |
| --- | --- |
| 安装 | 兼容条件、真实来源、依赖、重载风险和加载成功判据。 |
| 设置 | 全部字段、默认和范围可查，知道何时保存、生效与恢复。 |
| 审批与排障 | 能区分安全拒绝、规则命中、故障、超时、人工和取消，并知道下一步。 |
| 查记录 | 能分辨模型结论和最终结果，理解缺失、窗口、轮转、备份及写入失败。 |
| 停用卸载 | 能先换标准预设，备份并只清理目标条目，失败时恢复。 |
| 维护 | 能取得匹配源码，判断工具权限和副作用，按职责审查、验证与发布。 |

自动检查保护事实、结构、路径、占位符和显示关系。普通说明不冻结全文，也不以句长、关键词数量或长子串证明易读。每项检查要有能失败的反例。安全原文、稳定名称、协议与法律文本继续按职责精确检查。

独立测试从需求选择任务，不限于已有用例。视觉要求必须查看当前原图，结合真实页面行为和计算布局。旧夹具、接口响应、静态文件或单测不能冒充真实界面验证。

每次报告都区分通过、失败、跳过和未执行。退出码 0 不自动等于任务通过。文档修订、静态检查和离线测试，不表示宿主、模型、安全或发布已经通过验收。
